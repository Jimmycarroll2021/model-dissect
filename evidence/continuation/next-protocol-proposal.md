# Bounded next numerical protocol proposal

2026-11-17; advisory only. No model execution or implementation change. This advisor has read upstream/candidate sources and exposed results: all advice is source-assisted. Amendment requires independent protocol review; it is not already admitted by protocol-v1.

## Established failure and consequence

`runs/continuation/evaluation-strict-parity.json` contains 234/2640 failing rows: 204 logits and 30 final representations, all self cache/full comparisons, distributed over all 12 fixtures. Worst tolerance ratio is 2.108029842376709. Notably step 0 has no failing row; later steps do. The strict setting solved the sampled one-to-two-token case but did not solve general sequence/chunk invariance. Keep this receipt; it invalidates promotion to R3, not the usefulness of further bounded diagnosis. Same-mode equality still points toward shared execution arithmetic rather than an independent model mismatch.

The official [PyTorch numerical accuracy note](https://docs.pytorch.org/docs/2.15/notes/numerical_accuracy.html) allows different results across batched and sliced computation. [Intel strict-CNR conditions](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-c/2025-0/reproducibility-conditions.html) cover specified routines and thread-count reproducibility, not arbitrary cross-shape equivalence. Therefore more strict-mode successes cannot be assumed from the first case.

## Recommended amendment: two hypotheses, one selected candidate

Retain the original lifetime deadline, CPU FP32 preference, all numerical gates and cumulative resources. Explicitly supersede the previous stop-after-first-full-failure rule for this bounded continuation only. Allow at most two additional diagnostic processes, each at most 4096 reserved token positions and 300 seconds, including failed/invalid runs; no branching sweep. The existing unused third diagnostic can count as the first of these two, so this is one additional slot beyond the original total, not three new diagnostics. After diagnosis select at most one candidate, freeze it, and allow at most two complete R2 runs at 18000 tokens/600 seconds each, the second by an independent verifier. Reserve before execution. Keep a minimum 100000 remaining tokens for R3; do not restart elapsed or download budgets.

**D3: localize the first discrepancy beyond step 0; test threading once.** Use one old already-exposed unpadded fixture, length 8 with all four continuation steps (small enough for bounded captures). Run common strict two-thread baseline and one-thread strict in a single fresh diagnostic process only if thread changes are set before each independent model execution and recorded; preferably make the one-thread process the diagnostic and reuse existing two-thread tensors/receipts where sufficient. No general search of thread counts or instruction branches. Capture each block's Q/K/V projection, normalization, rotated Q/K, score product, masked scores, softmax and value product only at the first diverging token; compare old cached prefix K/V against full prefix. For a suspect primitive, replay the exact same input row standalone and in its original shape. Include row-wise SiLU/normalization as possibilities, not assumptions. Capture equality of effective allowed-key sets and positions. Localize discrepancies before interpreting the threading result.

Interpretation: if primitive discrepancy remains on identical inputs at one thread, a thread-partition-only explanation is rejected. If one thread resolves the exposed sequence, it is a minimal common-backend candidate, not proof for the full matrix. If earliest error is at attention after identical Q/K/V, linear-only fixes are unsupported. MKL_COMPATIBLE is not an additional admitted fallback: it would test another implementation without controlling PyTorch nonlinearities or attention reductions. Neither MKL branch choice nor single threading guarantees SiLU shape invariance.

**D4, only if needed and supported by D3: canonical per-token FP32 primitive dispatch.** First make an explicit execution-policy candidate, not a model-architecture rewrite. Evaluate a fixed token-row shape for the *localized* token-independent primitive (linear, RMSNorm or activation). If attention is responsible, use per-query score/value products over that query's causal prefix, retaining full key-mask semantics and genuine stored K/V. A full pass may compute each new token row; a cached pass must consume stored K/V and compute only newly submitted tokens. It must never replay the prefix through all model layers. Record operation counts/cache reuse to distinguish these behaviors. Do not eagerly canonicalize every operation or change reduction precision.

Canonical dispatch is mathematically honest when it preserves the same real-valued graph, masks, positions and KV state while declaring FP32 evaluation order. It is nevertheless a changed numerical execution policy and can be slower. Cropping future keys needs particular care: trim only keys excluded by causal negative infinity, not finite additive padding keys or any real token. Arbitrarily dropping padding would alter the registered computation. Independently prove the mask/index transformation on synthetic truth tables before model execution.

## Oracle integrity and acceptance

Prefer the one-thread common setting if D3 supports it, because native source and primitive implementations remain unchanged. Freeze source, environment, thread count and effective backend together. Do not claim success from a small case.

For a canonical primitive candidate, keep upstream vendor bytes immutable. A declared reference adapter policy may invoke independently implemented primitive scheduling around native layers, but cannot import the candidate implementation or use a shared global monkeypatch. Have an independent reviewer prove row mapping and cache behavior; compare native-reference versus policy-reference, and original-candidate versus policy-candidate under the unchanged registered tolerance at every boundary/logit on exposed fixtures, alongside primitive mathematical/shape checks. Preserve all failures. Common-policy candidate/reference equality alone is insufficient evidence because both could share a defect.

If changed-policy outputs fail the unchanged-native comparison, report that incompatibility explicitly. Do not quietly call the modified reference the original oracle or waive the comparison; further authority/spec clarification would be required to change what original-native reproduction means. There is no guarantee a new evaluation order meets every original-native per-element tolerance.

Freeze new private fixtures before the selected candidate's evaluation, preserve the original length/padding coverage and independent repeat, and retain no-op/restoration/top1/finiteness/cache/full requirements. The latest failed suite is now exposed diagnostic evidence; do not call a retest on its inputs fresh heldout. Run R3 only after complete R2 passes.

GPU FP32 without TF32 is a separate, lower-priority backend candidate, not an admitted extra trial. It would require live ownership/memory checks, common attention implementation, explicit precision settings, matched oracle execution and charging original GPU budgets; changing hardware does not promise cross-shape equivalence. No evidence presently justifies using it before the two bounded CPU hypotheses above.

Stop this amendment after two diagnostics plus the one selected candidate's full-suite failure, or any original cap/guard violation. Preserve a precise unresolved requirement conflict rather than expand into indefinite backend tuning.
