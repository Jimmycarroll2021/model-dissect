# GitHub tool landscape for the MiniMind investigation

Research snapshot: 2026-11-17. Candidate: TOOL-LANDSCAPE-001. This is a curated practical shortlist, not an exhaustive inventory of GitHub. The objective is the current specification: infer a supported tensor/computation map, build an independently executable reconstruction, compare it with a separate reference, and test one internal hypothesis. Improving EOS behaviour is not this objective.

**Recommendation:** start with PyTorch and its hooks, the checkpoint's native tensor reader, the MiniMind reference held by the evaluator, and the existing Spec Kit workflow. Add Netron for visual inspection when useful. These five components cover the first demonstration without requiring an interpretability framework port. NNsight is the first optional convenience layer; TransformerLens, pyvene, SAEs and circuit tracing are later additions justified by a specific need. This is an engineering judgment about dependency and adapter work, not a measured speed comparison or delivery-time guarantee.

Research only: no packages installed, weights downloaded, models run, training performed, or paid services used. Source documentation downloads are research receipts, not model acquisition. Exact installed environments, interoperability and numerical parity remain NOT_RUN.

## What each evidence source can establish

| Access tier | Useful tools | What becomes possible | Boundary |
|---|---|---|---|
| Checkpoint bytes, tensor names/shapes/dtypes/values | safetensors; GGUF reader; REA inventory | Inventory, storage layout, candidate tensor roles | Tensor containers do not uniquely encode execution order, nonlinearities, masking, positional computation, training history or semantics. Metadata hints must be labelled supplied or inferred. |
| Evaluator-controlled input/output and selected internal observations | PyTorch hooks; optionally NNsight or pyvene | Distinguish proposed computations and test interventions | Observation names/shapes themselves may reveal architecture; log each exposure. Hook access to the upstream module tree is evaluator access unless explicitly admitted. |
| An explicitly supplied executable graph | ONNX, Netron, Model Explorer, converters | Inspect or translate operations already represented in that graph | This is graph-assisted reconstruction; exporting the hidden reference and handing over its graph violates the current withheld-source boundary. |
| Target source/configuration | MiniMind, FX/export on the reference | Operate the reference and check structural claims | Evaluator-only oracle under the current protocol. Copying or wrapping its forward pass cannot count as inferred reconstruction. |
| Independently written candidate | PyTorch; optional FX/export/viewers | Inspect and validate our supported computation | A diagram generated from our candidate shows that candidate, not independent proof that the original works identically. |

Public MiniMind familiarity and this research exposure cannot be erased. Record prior knowledge and any architecture-bearing material exposed; label affected work prior-informed or source-assisted. Generic library reuse is compatible with inference, while importing the target's forward computation into the candidate is not.

## Smallest useful demonstration after execution admission

1. **Identify one compatible dense checkpoint and the allowed evidence.** Preserve full hashes, tensor inventory, tokenizer and reference/environment identities. Use the native reader; REA can supplement inventory receipts. Declare which source/config fields stay with the evaluator. No useful reconstruction starts with an unknown checkpoint identity.
2. **Freeze a tensor-to-computation map.** Account for every stored tensor as mapped or unresolved; separate direct observations, supplied facts, hypotheses and alternatives. Use evaluator-controlled observations to distinguish operations where weights alone are ambiguous. An unresolved required path blocks executable acceptance.
3. **Assemble the inferred forward computation from PyTorch primitives.** Write only the target-specific composition, mapping and evidence glue; reuse library tensor operations. Do not wrap upstream MiniMind forward. Run the separately operated reference and candidate through the existing R2 fixtures and internal boundaries; local hooks are sufficient initially.
4. **Investigate one internal hypothesis.** Choose a site and directional prediction from development observations, then freeze metric, effect threshold, no-op, matched internal control and restoration. Test on evaluator-held-out inputs. Accept supported, refuted or inconclusive as the honest investigative verdict; broad output damage does not establish a mechanism.
5. **Deliver the inspectable map, runnable candidate and independent receipts together.** Viewer output is supplementary. Preserve failures, numerical errors, exact identities, resource accounting and the verifier's verdict.

The existing specification owns the details: 12 parity fixtures (four lengths crossed with unpadded/left/right-padded inputs), cached/full-sequence comparison, embedding/block/final representation boundaries, FP32 backend and its stated tolerances; 16 development and 32 held-out probe inputs; the capped future budget. This research does not weaken those gates or claim feasibility has been measured. A first block comparison is an early debugging milestone, not completion of the whole demonstration.

The genuinely missing pieces are small but necessary: a controlled observation interface and disclosure ledger; tensor-role mapping; independent forward composition; model-specific site adapters; fixture/error reports; and budget/stop accounting. No repository here supplies those project-specific guarantees automatically. Building those seams is different from writing a tensor runtime, artifact parser or general interpretability library from scratch.
